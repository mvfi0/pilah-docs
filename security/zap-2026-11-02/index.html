    Security scan — OWASP ZAP per sub-issue, 2 Nov 2026¶

    Two scans with OWASP ZAP 2.17.0, one per Linear sub-issue finished this week, run right after the work was done:

    • PIL-428: void ("Hapus") a setoran;
    • PIL-435: Riwayat shows setoran only.

    Every finding was checked by hand, and each real one has a patch plan. Run for the IR Security competency (a Metasploit-or-similar scan, explained, with a patch plan). Since this week, every finished sub-issue gets one.

    Scope and authorisation

    My own local instances only. Staging and production were not scanned: an active scan sends thousands of attack requests.

    Scan Backend Web build
    PIL-428 feature/pil-428 (#145 at ae850a0) on 127.0.0.1:8451, scratch PostgreSQL 16 database zap428 #193 on 127.0.0.1:8452
    PIL-435 origin/staging at ee82c69, since PIL-435 changes no backend code, on 127.0.0.1:8453, scratch database zap435 #196 at 48f138b on 127.0.0.1:8454

    Both databases were migrated and filled by seed_testing_data, so they hold no real user data. The backends ran with DEBUG=true, so findings that need it are labelled debug-only.

    Method¶

    Each scan is one command: tools/zap_scan.py, with a small per-feature drive module (pil428.py, pil435.py).

    Step How
    Headless ZAP zap-2.17.0.jar -daemon with a scratch profile, API on 127.0.0.1:8090
    Signed in As the seeded demo Pengurus; a replacer rule adds the bearer token to every backend request ZAP sends
    Attack surface The OpenAPI schema imported, then the drive module's real requests sent through ZAP's proxy. For PIL-428: record two setoran, void one, void it again (409), void with an empty alasan (422), edit the voided one (409), read the list and riwayat. For PIL-435: the riwayat list for each tipe, with search, a custom period and the XLSX export. So the active scan attacks real ids and bodies, not schema placeholders
    Scans Spider of the API and web build, the passive scan, then the active scan limited to the feature: a ZAP context with /api/v1/transaksi (recursive: ids, /batalkan, PATCH) and /api/v1/aktivitas for PIL-428, and /api/v1/aktivitas and /api/v1/transaksi/export for PIL-435. Each recorded query-string variant was scanned on its own
    Verification Every 5xx in ZAP's history read from its response, not only ZAP's alerts; each real one reproduced with curl; the void's alasan tested by hand with attack payloads

    Reports: PIL-428 HTML and JSON; PIL-435 HTML and JSON. The script refuses to finish if a report holds a bearer token or a JWT, and I grepped all four as well.

    Results at a glance¶

    0 High in either scan. Every Medium and Low alert ZAP raised is either a known finding from the 26 Oct scan, still open on staging, or an artifact of the local servers:

    Alert Where Status
    CSP: Wildcard Directive (Medium) backend, every response Known: 26 Oct finding 2, still open
    Sub Resource Integrity Attribute Missing (Medium), Cross-Domain JavaScript Source File Inclusion (Low) /api/docs/ Known: 26 Oct finding 3, debug-only
    Application Error Disclosure (Low) /api/v1/pengumuman/id/tarik Known: 26 Oct finding 1, still open
    CSP Header Not Set, Missing Anti-clickjacking (Medium); X-Content-Type-Options Missing (Low) web build Local only: the static test server sends no headers. Production nginx does, and Pascal's #178 adds a full CSP
    Server Leaks Version Information (Low) both Local only: the dev servers' banners
    User Agent Fuzzer, Modern Web Application and others (Info) both Informational

    No alert on the features themselves:

    • The void: no injection, path traversal or error disclosure on /transaksi, /transaksi/{id}, /batalkan or PATCH. PIL-428's scan sent about 8,000 requests in scope: 5,800 on /transaksi (about 260 on /batalkan, 610 PATCH) and 2,200 on /aktivitas.
    • The riwayat list and export: none on /aktivitas or the export either. PIL-435's scan sent about 7,000 requests there.

    ZAP's alerts aren't the whole story, though. Reading every response in its history turned up three 5xx that ZAP didn't raise as alerts:

    # Request Response Real or local?
    1 GET /api/v1/aktivitas?search=…%00… (JSON) 500, DataError: PostgreSQL text fields cannot contain NUL (0x00) bytes Real, in production too
    2 GET /api/v1/aktivitas with Accept: text/html 500, AssertionError: 'ActivityHistoryView' should either include a queryset attribute… Debug-only
    3 GET /api/v1/transaksi/{id} with Accept: text/html 500, AttributeError on field alasan of TransactionEditSerializer Debug-only

    Findings¶

    # Finding OWASP Severity Whose code
    1 A NUL byte in ?search= crashes six list endpoints with a 500 instead of a 422 A04 (2021); A10 Mishandling of Exceptional Conditions (2025) Low–Medium The list views from PIL-246 onwards (Rifqi, Pascal, others); activity_sources is the riwayat's, which PIL-435 uses
    2 The browsable API crashes on /aktivitas A05 Low (debug-only) ActivityHistoryView (PIL-246)
    3 The browsable API crashes on a setoran's detail A05 Low (debug-only) TransactionEditSerializer (PIL-427)

    1. NUL byte in search: a 500 on six endpoints¶

    Reproduced by hand on the PIL-428 backend, as the demo Pengurus, with plain JSON requests:

    $ curl -H "Authorization: Bearer …" -H "Accept: application/json" ".../api/v1/aktivitas?search=ab%00c"
500
$ # the same for /transaksi, /transaksi/export, /pencairan, /nasabah and /jenis-sampah
$ curl ... ".../api/v1/aktivitas?search=abc"
200

    Cause. Each list view reads search straight from the query string (request.GET.get("search", "")) and passes it to an icontains filter. PostgreSQL refuses text containing \0, and the DataError escapes as a 500.

    Request bodies don't have this problem, because they go through DRF fields. The void's alasan with a NUL byte gets 422 "Karakter null tidak diizinkan.", from CharField's built-in ProhibitNullCharactersValidator.

    Impact. No data is exposed: with DEBUG=false the body is a generic 500. But it's an unhandled exception any signed-in user can trigger at will, and each one logs an error. Rifqi's open #144 already validates the nasabah list's search with a CharField, which would turn that one endpoint into a 422 once merged. The other five remain.

    2 and 3. Browsable-API crashes, debug-only¶

    config/settings.py adds BrowsableAPIRenderer only when DEBUG is on, so these can't happen in production. Locally, anyone opening the API in a browser hits a 500:

    • ActivityHistoryView is a GenericAPIView without a queryset;
    • the setoran detail renders its PATCH form from TransactionEditSerializer, whose alasan is write-only input, not a model attribute.

    Both also fail on unmodified staging (checked against ee82c69).

    What held up¶

    • The void's state machine: every attack POST on /batalkan got 409 (already void) or 422 (bad alasan). The database afterwards held exactly the voids the drive made, one per run, with its own alasan, so no payload voided a setoran or changed a saldo. The roughly 610 PATCH attacks on the voided setoran got 409 or 422.

    • The alasan as data, checked by hand on fresh setoran:

      Input Result
      <script>alert(1)</script>, ' OR 1=1; DROP TABLE transaksi;--, =HYPERLINK("http://x","y") 200, stored and returned verbatim as JSON text: the ORM parameterises it, and Flutter renders it as plain text
      A NUL byte 422
      256 characters 422 (255 is accepted)
      Only whitespace 422 "Alasan pembatalan wajib diisi"
      An unknown or malformed id 404

      A voided setoran never appears in the XLSX or the statement PDF, so a formula in the alasan can't reach a spreadsheet. The exporter also guards user text against formulas. - Bank scoping: another bank's setoran is 404, covered by the tests in f67aa72. ZAP signs in as one user, so it doesn't test this itself.

    Patch plan¶

    Each fix is test-first, with its OWASP category in the commit.

    # Fix Test first OWASP Status (2 Nov)
    1 Validate list query text the way bodies are: a shared helper in shared_kernel that reads search through a DRF CharField (NUL rejected, length bounded) and answers 422. All six list views use it For each of the six endpoints: ?search=a%00b gets 422, never 500; a normal search still filters A04 / A10:2025 Planned. It touches several teammates' views, so it needs a Linear issue first
    2 Give ActivityHistoryView the shape the browsable API expects, or set renderer_classes = [JSONRenderer] on it With DEBUG=True overridden, Accept: text/html on /aktivitas gets 200 or 406, not 500 A05 Planned, low priority (debug-only)
    3 Render the detail's browsable form without TransactionEditSerializer's write-only alasan: mark it write_only=True Accept: text/html on a setoran's detail gets 200 under DEBUG=True A05 Planned, low priority (debug-only)
    — 26 Oct findings 1–3 (the announcement 500, the backend CSP, Swagger SRI) As in that plan A04, A05, A08 Still open on staging; this scan re-confirmed them

    How the method improved on 26 Oct¶

    The 26 Oct scan imported the schema, so ZAP attacked paths like /transaksi/id/batalkan, which can only ever 404. This time:

    • Real requests: the drive module sent the feature's real requests through ZAP's proxy, so the scan attacked a real setoran's void and edit.
    • History, not only alerts: reading every response in ZAP's history found the NUL-byte crash, which ZAP doesn't report as an alert.

    Three mistakes on the way, corrected before trusting the results:

    • Git Bash rewrote --scope /api/... into a Windows path, so the first runs had nothing in scope.
    • ZAP's active-scan API can't find id paths by URL, so the script now scans each prefix recursively.
    • Its report API needs | between sites, not ;, so the first reports came out empty.

    The script now refuses a non-API scope and fails on an empty report.
