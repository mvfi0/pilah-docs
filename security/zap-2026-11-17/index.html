    Security scan — OWASP ZAP per sub-issue, 17 Nov 2026¶

    Three scans with OWASP ZAP 2.17.0, one per backend PR opened on 16 Nov for Sprint 3 Week 3:

    • PIL-482 (#175): a malformed nasabah_id on /transaksi and /pencairan answers 422, not 500. This is the fix for 9 Nov finding 1;
    • waste categories through tercatat() (#176): /dashboard/waste-categories reads counted setoran through the named rule;
    • a NUL byte in a request body (#177): kode on jenis-sampah and nasabah edits, and the device token on DELETE /device-tokens/, answer 422, not 500.

    Every 5xx the backends answered was read and classified. The scans ran from 16 Nov 23:56 to 17 Nov 00:26. Run for the IR Security competency (a Metasploit-or-similar scan, explained, with a patch plan), as for every finished sub-issue since 2 Nov.

    Scope and authorisation

    My own local instances only. Staging and production were not scanned.

    Scan Backend Database
    PIL-482 feature/pil-482 (#175 at b85819a) on 127.0.0.1:8482 zap482
    waste-categories fix/waste-categories-tercatat (#176 at 8d1a931) on 127.0.0.1:8483 zapwaste
    nul-body fix/nul-in-request-body (#177 at 7b7841d) on 127.0.0.1:8484 zapnul
    • Databases: each is a scratch PostgreSQL 16 database, created fresh, migrated and filled by seed_testing_data, so none holds real user data.
    • No web build: none of the three PRs changes the UI.
    • Clean environment: each backend ran with DEBUG=true but was started with an empty environment (env -i plus only the variables it needs). So no secret of the dev machine could reach a debug page, unlike on 9 Nov.

    Method¶

    The same one-command driver as on 9 Nov, tools/zap_scan.py, with one new drive module per PR: pil482.py, waste_categories.py, nul_body.py.

    Step How
    Headless ZAP zap-2.17.0.jar -daemon with a 1 GB heap, API on 127.0.0.1:8090; one scan at a time, each with its own backend and a new ZAP session
    Signed in As the seeded demo Pengurus; a replacer rule adds the bearer token to every backend request ZAP sends
    Attack surface The OpenAPI schema imported, then the drive module's real requests sent through ZAP's proxy:
    • PIL-482: each ledger list with a real member's id (200) and with abc (422).
    • waste-categories: record two setoran, void one, then read waste-categories, the trends and the stats.
    • nul-body: edit a jenis and a nasabah keeping their own kode (200), with a NUL in it (422) and with another record's kode padded with spaces (422); register a device token, then forget it with a NUL token (422) and with the real one (204)
    Scans Spider of the API, the passive scan, then the active scan limited to each PR's paths by a ZAP context:
    • PIL-482: /api/v1/transaksi, /api/v1/pencairan, /api/v1/aktivitas.
    • waste-categories: /api/v1/dashboard/waste-categories.
    • nul-body: /api/v1/jenis-sampah, /api/v1/nasabah, /api/v1/device-tokens.
    Each recorded query-string variant was scanned on its own
    Requests Counted from each backend's own request log, which sees every request ZAP sent:
    • PIL-482: 17,059 in all, including 1,781 on the /transaksi list, 1,681 on the /pencairan list and 2,766 on /aktivitas.
    • waste-categories: 1,523, of which 1,056 on /dashboard/waste-categories.
    • nul-body: 30,674, including 231 attacks on the real jenis's PATCH and 228 on the real nasabah's
    Verification Every 5xx in the three backend logs read from its traceback and sorted into real, debug-only, or caused by my machine

    Reports:

    Scan HTML JSON
    PIL-482 HTML JSON
    waste-categories HTML JSON
    nul-body HTML JSON

    The driver refused to finish on any bearer token, JWT, webhook, API token or database URL with a password. By hand I also searched all six files for the computer name and my user name. None of these appear, so nothing was redacted.

    Results at a glance¶

    No High alert in any of the three scans, and no new finding. Every alert is one already on record:

    ZAP alert Where Verdict
    CSP: Wildcard Directive (Medium) backend, five paths Known: 26 Oct finding 2, still open
    Sub Resource Integrity Attribute Missing (Medium), Cross-Domain JavaScript Source File Inclusion (Low) /api/docs/ Known: 26 Oct finding 3, debug-only
    Server Leaks Version Information (Low) all three backends Local only: the dev server's banner
    Authentication Request Identified, Session Management Response Identified, User Agent Fuzzer, Modern Web Application (Info) all three Informational

    What each PR's scan shows¶

    • PIL-482, the fix for 9 Nov finding 1. ZAP sent 965 malformed nasabah_id values to the /transaksi and /pencairan lists, counting the value Django reads when a parameter repeats. All 965 got 422 and none got 500.
      • Before the fix: on 9 Nov the scan of /transaksi alone gave 226 of these 500s, and they caused two false High alerts (Server Side Include, Padding Oracle). Neither alert came back.
      • The other 422s: another 1,067 carried a valid id while ZAP attacked a different parameter (periode, tipe, dates).
      • Empty value: an empty nasabah_id= means no filter and got 200.
      • /aktivitas: its 487 malformed ids got 422, as before.

    • waste-categories. ZAP sent 1,056 requests to /dashboard/waste-categories, attacking dates, ranges and injections in each parameter:

      • 1,003 got 400 for an invalid date or range;
      • 50 got 200;
      • 3 got 404.

      There was no 5xx and no alert on the path. The PR changes which rule selects the rows, not the response, so the scan's job here was to show that nothing new opened. - nul-body. The attacks on the real jenis's and the real nasabah's PATCH were answered 200, 422 or 405, never 500. On staging a NUL or a padded duplicate kode in that body is a 500 (DataError, IntegrityError); the drive module showed both now give 422.

    Findings¶

    No new finding. The state of the earlier ones that these PRs touch:

    Earlier finding Status after this scan
    9 Nov 1: malformed nasabah_id is a 500 on /transaksi Fixed by #175: all 965 malformed ids got 422, none 500 (open for review; filed as PIL-482)
    9 Nov 2 / 2 Nov 1: a NUL byte in search is a 500 Fixed on staging by #172 (Scallss, 16 Nov). #177 fixes the request-body case #172 left open, plus a padded duplicate kode that was also a 500
    9 Nov 3: the browsable API crashes on /aktivitas Still open, debug-only; seen again here (row 1 above)
    26 Oct 2 and 3: CSP wildcard, /api/docs/ without SRI Seen again on these branches, which predate the fix. Finding 3 is fixed on staging by Gabriel's #174, merged 17 Nov after these scans; finding 2 is still open

    Limits¶

    • DELETE /device-tokens/ was not actively scanned. That route is only ever sent POST and DELETE, so ZAP's site tree has no GET node for it. ZAP refused the active scan ("URL Not Found in the Scan Tree") both by prefix and per method. Its NUL case is covered instead by the drive module's own request (NUL token, 422) and by #177's tests. Scanning it needs a change to how the driver starts scans; that is in the patch plan.
    • Coverage of the scans: each scan covers the paths in scope, as one signed-in Pengurus, with DEBUG=true. They don't test another bank's data, which is covered by the unit tests.
    • Many requests went to placeholder paths. Requests built from the OpenAPI schema use literal placeholders (/nasabah/id/approve), which answer 404. So the attacks that count are the ones on the real records the drive module created. Their numbers are given above.

    Patch plan¶

    # Fix Test first OWASP Status (17 Nov)
    1 Merge #175, #176 and #177 Each PR's own tests: red, then green, in its commits A04 / A10:2025 Open for review; CI and SonarCloud green on all three (100% new coverage, 0 issues)
    2 renderer_classes = [JSONRenderer] on ActivityHistoryView Accept: text/html on /aktivitas under DEBUG=True gets 200 or 406, not 500 A05 Planned, low priority (debug-only); carried from 9 Nov item 3
    3 Let tools/zap_scan.py actively scan a path that has no GET node (e.g. start from the recorded message, or add the node by a GET request first) Rescan /device-tokens/: more than 0 scans start, and every response is 2xx or 4xx — Planned (tooling)
    — 26 Oct findings 2 and 3 As in that plan A05, A08 Still open on staging

    What went wrong on the way¶

    • The first attempt on 16 Nov ran out of machine. Two full test suites, three backends and ZAP ran at the same time and used up the 16 GB machine's commit memory. PostgreSQL stopped with Windows error 1455, and later ZAP died with a native OutOfMemoryError ("malloc failed"). The disk on C: also reached 0 GB free.
      • Evidence discarded: the PIL-482 files from that attempt (zap-pil-482-2026-11-16.*) record attacks on a dead database, so they are not used or published.
      • The rerun: after the disk was freed, all three scans were run again, one at a time:
        • each database was recreated from the seed;
        • ZAP's heap was capped at 1 GB;
        • the test suites waited for the scans to finish.
    • A bug in the scan runner. It exported MSYS_NO_PATHCONV=1 for the whole script. In Git Bash that broke the curl -o /dev/null readiness check, so the runner waited forever. The variable is now set only on the zap_scan.py command.
