    Security scan — OWASP ZAP per sub-issue, 23 Nov 2026¶

    One scan with OWASP ZAP 2.17.0 of PIL-539, a nasabah who already belongs to a bank sampah applying to another one, run right after the sub-issue was finished:

    • backend: pilah-be #185 (merged 23 Nov), tests for the flow on the existing endpoints;
    • mobile: pilah-mobile #276, "Ajukan bank baru" on Bank sampah saya. It calls GET /nasabah/me, GET /bank-sampah and POST /onboarding/nasabah.

    This is the first scan signed in as a nasabah rather than the demo Pengurus, because the flow is the nasabah's. Every 5xx the backend answered was read and classified. The scan ran on 23 Nov from 00:44 to 00:52, after a first run that showed a gap in the tooling (see What went wrong).

    Scope and authorisation

    My own local instance only. Staging and production were not scanned.
    Backend staging at 80a30aa (the #185 merge) on 127.0.0.1:8539
    Database Scratch PostgreSQL 16 database zap539, created fresh, migrated and filled by seed_testing_data, plus one extra active bank sampah ("Bank Sampah ZAP Kedua") so the demo nasabah has a second bank to apply to. No real user data
    Signed in as customer.demo@example.com, the seeded nasabah, approved at "Bank Sampah PILAH E2E"
    Environment DEBUG=true, started with an empty environment (env -i plus only the variables it needs), as since 17 Nov
    Web build None: #276 changes only native Nasabah screens

    Method¶

    One command, tools/zap_scan.py, with the drive module pil539.py, and --id-token dev:customer.demo@example.com:… so the bearer rule carries the nasabah's token.

    The drive module sends the flow's real requests through ZAP's proxy:

    Request Answer
    GET /api/v1/nasabah/me 200, one approved membership
    GET /api/v1/bank-sampah 200, the directory
    POST /api/v1/onboarding/nasabah with the second bank 201, pending
    the same again 400, "Anda sudah terdaftar sebagai nasabah di bank sampah ini"
    with the nasabah's own bank 400, the same message
    with bank_sampah_id: "bukan-uuid" 422
    GET /api/v1/nasabah/me 200, two memberships
    GET /api/v1/nasabah/me/saldo?keanggotaan_id=<pending> 403: a pending membership can't open its saldo

    Then the spider, the passive scan, and an active scan limited to /api/v1/onboarding/nasabah, /api/v1/nasabah/me (recursive) and /api/v1/bank-sampah (recursive). The POST-only path is scanned from its recorded request, with its method and the drive's body: this is the tooling fix from this scan.

    Reports: HTML and JSON. Both were checked by the script's secret patterns (none) and for the machine's and my user name (none). The clean environment meant there was nothing to redact.

    Results at a glance¶

    No High alert, and no new finding. Every alert is one already on record:

    ZAP alert Where Verdict
    CSP: Wildcard Directive (Medium) backend, five paths Known: 26 Oct finding 2, still open
    Server Leaks Version Information (Low) backend Local only: the dev server's banner
    User Agent Fuzzer (Info) POST /api/v1/onboarding/nasabah Informational. It is also the proof that the POST-only path was actively attacked this time
    Authentication Request Identified, Modern Web Application (Info) auth paths, /api/docs/ Informational

    What the scan shows on the feature's paths¶

    From the backend's own log, which sees every request ZAP sent:

    Path Requests Answers
    POST /api/v1/onboarding/nasabah 228 POSTs: 224 attacks and the drive's four 207 × 422, 19 × 400, 1 × 404, and one 201, the drive's own. No 5xx, and no attack created a membership: afterwards the nasabah has exactly the two rows the drive made (approved at bank A, pending at bank B). The attacks used the real body, {"bank_sampah_id": "<bank B>"}, with injection, path-traversal and header payloads in the value
    /api/v1/nasabah/me and children about 4,000 200, 403, 404, 405, 422 and 3 × 429 (the per-user throttle). 3 × 500, below
    /api/v1/bank-sampah and children about 2,490 200, 400, 403, 404, 405, 422. Every write a nasabah tried was refused: 1,926 × 403 on PUT and 6 on POST

    ZAP's alerts aren't the whole story¶

    Every 5xx in the backend log:

    # Request Response Real or local?
    1 GET /api/v1/nasabah/me/riwayat (×3, with and without query) and Accept: text/html 500, AssertionError: 'NasabahHistoryView' should either include a queryset attribute… from DRF's BrowsableAPIRenderer.get_filter_form Debug-only. The same crash as 2 Nov finding 2 and 9 Nov finding 3, now seen on the nasabah's riwayat. The browsable renderer is only added when DEBUG is on; production serves JSON only
    2 GET /api/v1/auth/google/start 503, "Google OAuth client is not configured" Local only: the scratch backend has no Google client id

    Findings¶

    No new finding. The state of the earlier ones this scan touched:

    Earlier finding Status
    9 Nov 3 / 2 Nov 2: the browsable API crashes on list views without a queryset Still open, debug-only. Seen again on NasabahHistoryView
    26 Oct 2: CSP wildcard directive Still open
    17 Nov limit: a POST- or DELETE-only path can't be actively scanned Fixed in the tooling in this scan, see below

    What held up¶

    • One membership per bank, on the server. #276 removed the client's one-bank lock for this flow. The duplicate rule lives in register_nasabah, and 224 attacks on the application endpoint produced no second row and no 5xx.
    • A pending membership opens nothing. Its saldo answers 403, as pinned by #185's tests.
    • The directory is read-only for a nasabah. Every PUT and POST under /bank-sampah was refused.

    Limits¶

    • One account. The scan runs as one nasabah. It doesn't test another nasabah's memberships or a pengurus deciding the application; those are in #185's tests.
    • Placeholder paths. Requests built from the OpenAPI schema use literal placeholders (/nasabah/id/saldo), which answer 404. The attacks that count are on the real records the drive module created.
    • No native client. #276 is a native screen, so no web build was spidered.

    Patch plan¶

    # Fix Test first OWASP Status (23 Nov)
    1 renderer_classes = [JSONRenderer] on the nasabah history view, as planned for ActivityHistoryView Accept: text/html on /nasabah/me/riwayat under DEBUG=True gets 200 or 406, not 500 A05 Planned, low priority (debug-only); joins 9 Nov item 3
    2 tools/zap_scan.py scans a POST- or DELETE-only scope path from its recorded request Rescan: the path is attacked (User Agent Fuzzer on it, 224 attack requests in the log) — Done (23 Nov), closes 17 Nov plan item 3
    — 26 Oct finding 2 As in that plan A05 Still open on staging

    What went wrong on the way¶

    • The first run left the endpoint that matters unscanned. ZAP refused POST /onboarding/nasabah with "URL Not Found in the Scan Tree". It's the same limit as /device-tokens/ on 17 Nov: a path only ever sent POST has no GET node to look up. I started that scan by hand through ZAP's API with the method and body, which worked. Then I fixed zap_scan.py to do it itself, rebuilt the database and reran everything. This report is from the rerun.
    • The driver's log line was wrong. It always said "signed in as the seeded demo Pengurus". It now names the account the token belongs to.
    • I stopped the scratch PostgreSQL by mistake. It was recovering after the session's earlier shutdown, and I deleted its postmaster.pid, so it shut itself down as soon as it was ready. It restarted cleanly with its log outside the data directory, before any scan request was sent.
