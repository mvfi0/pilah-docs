    Security scan — OWASP ZAP per sub-issue, 9 Nov 2026¶

    Two scans with OWASP ZAP 2.17.0, one per Linear sub-issue finished today, run right after the work was done:

    • PIL-481: a voided ("Hapus") setoran is hidden from the riwayat lists;
    • PIL-480: the riwayat export no longer has the "ID Aktivitas" column.

    Every High alert was checked by hand, every 5xx in ZAP's history was read, and each real finding has a patch plan. Run for the IR Security competency (a Metasploit-or-similar scan, explained, with a patch plan), as for every finished sub-issue since 2 Nov.

    Scope and authorisation

    My own local instances only. Staging and production were not scanned: an active scan sends thousands of attack requests.

    Scan Backend Web build
    PIL-481 feature/pil-481 (#167 at 646c0d1) on 127.0.0.1:8451, scratch PostgreSQL 16 database zap481 #238 at ff86f6f on 127.0.0.1:8452
    PIL-480 feature/pil-480 (#168 at 2b1fba9) on 127.0.0.1:8453, scratch database zap480 none: PIL-480 changes no UI

    Both databases were migrated and filled by seed_testing_data, so they hold no real user data. The backends ran with DEBUG=true, so findings that need it are labelled debug-only. The web build is a static site, so ZAP could only spider its files.

    Method¶

    Each scan is one command: tools/zap_scan.py, with a small per-feature drive module (pil481.py, pil480.py).

    Step How
    Headless ZAP zap-2.17.0.jar -daemon, API on 127.0.0.1:8090
    Signed in As the seeded demo Pengurus; a replacer rule adds the bearer token to every backend request ZAP sends
    Attack surface The OpenAPI schema imported, then the drive module's real requests sent through ZAP's proxy. PIL-481: record two setoran, void one, then read /transaksi, /aktivitas, the dashboard's recent transactions and the detail of the voided and the kept setoran. PIL-480: the XLSX export with every period, tipe, member, search and custom-range filter, plus a bad periode (400), and the riwayat list it is built from
    Scans Spider of the API (and the web build for PIL-481), the passive scan, then the active scan limited to the feature by a ZAP context. PIL-481: /api/v1/transaksi (recursive: ids, /batalkan, PATCH), /api/v1/aktivitas, /api/v1/dashboard/recent-transactions. PIL-480: /api/v1/transaksi/export and /api/v1/aktivitas. Each recorded query-string variant was scanned on its own
    Requests in scope PIL-481: 7,590 on /transaksi (444 of them on /batalkan), 3,774 on /aktivitas, 28 on the dashboard list. PIL-480: 4,835 on the export, 2,189 on /aktivitas. These are from the second run; see "What went wrong" for why there were two
    Verification Every High alert reproduced by hand; every 5xx in ZAP's history read from its response (not only ZAP's alerts) and sorted into real, debug-only, or caused by my machine

    Reports: PIL-481 HTML and JSON; PIL-480 HTML and JSON. One alert's evidence is a Django debug page that dumps the dev machine's environment, so I redacted the computer name and my user name from the saved files. That was not enough: the dump also held two Discord webhook URLs, and they were published with the report. See "What went wrong" for how that was caught and fixed; the files now carry [REDACTED] in their place, and nothing else was edited.

    Results at a glance¶

    Neither feature has a real High. ZAP raised three High alerts in the first PIL-481 run, two in the second, and none in PIL-480 either time. All are false positives; the 500 behind two of them is a real finding that was already in the code (finding 1 below).

    ZAP alert Where Verdict
    SQL Injection (High) POST /transaksi/{id}/batalkan, parameter alasan, payload John Doe' AND '1'='1' -- False positive, see below. It did not recur in the second run
    Server Side Include (High) GET /transaksi?nasabah_id=<!--#EXEC cmd="dir \"--> False positive: the "evidence" is Django's DEBUG error page listing the dev machine's environment, not an executed command. The real cause is finding 1
    Generic Padding Oracle (High) GET /transaksi?nasabah_id=…w1 False positive: nothing is encrypted; ZAP matched the text "Internal Server Error". Same real cause: finding 1
    CSP: Wildcard Directive (Medium) backend, five paths Known: 26 Oct finding 2, still open
    Sub Resource Integrity Attribute Missing (Medium), Cross-Domain JavaScript Source File Inclusion (Low) /api/docs/ Known: 26 Oct finding 3, debug-only
    Application Error Disclosure (Low) /api/v1/pengumuman/{id}/tarik Known: 26 Oct finding 1, still open
    CSP Header Not Set, Missing Anti-clickjacking (Medium); X-Content-Type-Options Missing (Low) web build Local only: the static test server sends no headers. Production nginx does
    Server Leaks Version Information (Low) both backends and the web build Local only: the dev servers' banners
    Authentication Request Identified, Session Management Response Identified, User Agent Fuzzer, Modern Web Application (Info) both Informational

    No alert on the features themselves: none on /transaksi, /aktivitas, the dashboard list, /batalkan or the export that points at what PIL-481 or PIL-480 changed.

    The "SQL injection" on the void's alasan, reproduced by hand¶

    In the first run ZAP reported that two payloads gave different pages (the second run did not raise it again). Both payloads sent by hand, each on its own fresh setoran:

    Request Result
    alasan = John Doe' AND '1'='1' -- 200, voided
    alasan = John Doe' AND '1'='2' -- 200, voided
    the same setoran voided again 409

    Both rows are dibatalkan and the stored alasan is the payload text, character for character (the field only trims the trailing space). So the two payloads behave identically; ZAP's "different pages" came from the state change: the first request it sent voided the setoran (200), and every attack variant after it hit an already-voided setoran (409). The ORM parameterises the value, as in the 2 Nov hand test.

    The export file, checked by hand¶

    GET /transaksi/export?periode=semua on the PIL-480 backend returned 200 with a valid workbook: sheets Laporan, Riwayat Transaksi, Ringkasan; the raw sheet has 13 columns, headers No … Pencairan (Rp), no "ID Aktivitas", and the title rows merged over A1:M1 and A2:M2.

    ZAP's alerts aren't the whole story¶

    Reading every response in ZAP's history of the second run gave 268 5xx in the PIL-481 scan and 5 in PIL-480. Sorted, with none caused by the machine:

    # Request Response Real or local? PIL-481 / PIL-480
    1 GET /api/v1/transaksi?nasabah_id=<not a UUID> 500, ValidationError: '…' bukan UUID yang valid Real, in production too; reproduced on the PIL-480 backend, which has staging's code for this path 226 / 0
    2 GET /api/v1/transaksi, /aktivitas, /transaksi/export with a NUL byte in search 500, DataError: PostgreSQL text fields cannot contain NUL (0x00) bytes Real, known: 2 Nov finding 1, now also on the export 2 / 2
    3 GET /api/v1/aktivitas and GET /api/v1/transaksi/{id} with Accept: text/html 500, AssertionError / AttributeError Debug-only, known: 2 Nov findings 2 and 3 38 / 1
    4 POST /api/v1/pengumuman/{id}/tarik with a malformed id 500, ValueError Real, known: 26 Oct finding 1 1 / 1
    5 GET /api/v1/auth/google/start 503, "Google OAuth client is not configured" Local only: the scratch backends have no Google client id 1 / 1

    Rows 1–4 are not caused by PIL-481 or PIL-480.

    Findings¶

    # Finding OWASP Severity Whose code
    1 A malformed nasabah_id on GET /transaksi is a 500, while the same value on /aktivitas is a 422 A04 (2021); A10 Mishandling of Exceptional Conditions (2025) Low–Medium TransaksiViewSet.get_queryset filters on the raw query value. Not changed by PIL-481, which only added .tercatat() to the list
    2 A NUL byte in ?search= is a 500 on the list endpoints, now also seen on the export A04; A10:2025 Low–Medium Known: 2 Nov finding 1, still open
    3 The browsable API crashes on /aktivitas and a setoran's detail A05 Low (debug-only) Known: 2 Nov findings 2 and 3
    4 With DEBUG=true the 500 page lists the whole process environment A05 Low (debug-only) DEBUG is off in staging and production; this is why the report files had to be redacted

    1. Malformed nasabah_id: a 500 on GET /transaksi¶

    $ curl -H "Authorization: Bearer …" -H "Accept: application/json" ".../api/v1/transaksi?periode=semua&nasabah_id=abc"
500
$ curl ... ".../api/v1/aktivitas?periode=semua&nasabah_id=abc"
422

    Cause. TransaksiViewSet.get_queryset does qs.filter(nasabah_id=nasabah_id) with the raw query value, so Django's ValidationError escapes as a 500. activity_sources (the riwayat) already validates the same parameter with serializers.UUIDField, which is why /aktivitas answers 422.

    Impact. No data is exposed with DEBUG=false: the body is a generic 500. But any signed-in user can trigger an unhandled exception at will, and each one logs an error. It also made ZAP raise two of the three High alerts above, which is how it was found.

    What held up¶

    • PIL-481, hiding a void: the lists leave it out and the detail by id still answers with the void, checked by the end-to-end run in #238 (24/24) and by the tests in #167. Hiding is a filter, so the audit row, who voided it, when and why are untouched.
    • PIL-480, the export: the file no longer carries any setoran or pencairan id, which is the point of A02 here: a workbook that gets forwarded by chat or email leaks no internal record ids. "ID Nasabah" (the member number) stays.
    • The void's alasan as data: stored verbatim, never executed, as in the 2 Nov hand test.

    Limits¶

    • What the scans cover: the paths in scope, as one signed-in Pengurus, with DEBUG=true on a scratch database. They don't test another bank's data (that is in the unit tests) or the web build's API calls: the web build is a static site, so ZAP only spidered its files.
    • The first run was incomplete and was replaced. The machine's disk was full and the scratch PostgreSQL ran out of memory, so about 160 attack responses were local failures (see "What went wrong"). I re-ran both scans after the disk was freed. The second run had no such failure, and its results are the ones in this report.

    Patch plan¶

    Each fix is test-first, with its OWASP category in the commit.

    # Fix Test first OWASP Status (9 Nov)
    1 In TransaksiViewSet.get_queryset, validate nasabah_id with serializers.UUIDField().run_validation, as activity_sources does, and answer 422 ?nasabah_id=abc and ?nasabah_id=<script> on /transaksi get 422, never 500; a valid id still filters A04 / A10:2025 Planned. Filed as PIL-482 (9 Nov); it touches the list view of other issues, so it is its own PR
    2 Shared helper in shared_kernel that reads search through a DRF CharField (NUL rejected, length bounded) for every list view and the export For each endpoint: ?search=a%00b gets 422, never 500 A04 / A10:2025 Planned (2 Nov patch plan, item 1)
    3 renderer_classes = [JSONRenderer] on ActivityHistoryView, and write_only=True on TransactionEditSerializer.alasan Accept: text/html on both under DEBUG=True gets 200 or 406, not 500 A05 Planned, low priority (debug-only)
    4 Nothing to change in code: DEBUG is off in staging and production (DJANGO_DEBUG = "false" in fly.toml). Keep scan reports redacted — A05 Closed, kept for the record
    — 26 Oct findings 1–3 As in that plan A04, A05, A08 Still open on staging; this scan re-confirmed them
    — Re-run both scans once the disk was freed Zero OperationalError or No space left in the second run — Done (9 Nov)

    What went wrong on the way¶

    • ZAP's first start installs its add-ons and moves its API from 8090 to 8080 and back, so the first two scan attempts failed on "connection refused" and "remote end closed". The scans were started again once ZAP listened on 8090.
    • The first full run was partly invalid. The machine's disk filled up (No space left on device on the export), and the scratch PostgreSQL ran out of memory with three backends and ZAP's four threads attacking it: 140 of the PIL-481 scan's 5xx and 19 of PIL-480's were OperationalError or OSError. I classified them as the machine's fault, not findings, and re-ran both scans after the disk was freed. The second run had none, and the alerts differed only in that the "SQL injection" on alasan did not recur.
    • Both runs' report files held a Django debug page with the dev machine's environment, so the computer name and my user name were redacted from the saved files each time.
    • A secret got through (found 13 Nov). The same environment dump held two Discord webhook URLs (the review and QA channels' DISCORD_*_WEBHOOK_URL variables, exported on the dev machine), and the PIL-481 HTML and JSON were pushed with them in commit 04c1939. My check at the time looked only for bearer tokens and JWTs, and my "grepped for secrets" did not cover webhooks. GitHub's public-repo scanning (FriendlyScanner) found them within a day and Discord deleted both webhooks, so they no longer work. The four other credential variables in the dump (DB_PASSWORD, DJANGO_SECRET_KEY, HTTP_AUTHORIZATION, PILAH_ALLOW_FAKE_GOOGLE_TOKEN) were already masked by Django. The fix: the two files now say [REDACTED]; tools/zap_scan.py now also refuses to finish on Discord and Slack webhooks, GitHub, Google and Slack tokens, and database URLs with a password, and I confirmed the new check flags the original file and none of the current ones. The OWASP category is A05 Security Misconfiguration, as in finding 4 (a debug page that dumps the environment); the old commit 04c1939 still contains the dead URLs.
