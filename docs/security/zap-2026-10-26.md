# Security scan — OWASP ZAP, 26 Oct 2026

A dynamic scan of the PILAH backend (`pilah-be`) and the web build (`pilah-mobile`) with **OWASP ZAP 2.17.0**, followed by manual verification of every finding and a patch plan. It's the follow-up to the [14 Oct Metasploit scan](index.md), run for the IR Security competency (a Metasploit-or-similar scan, explained, with a patch plan).

!!! note "Scope and authorisation"
    I scanned **my own local instances only**:

    - the backend from the PIL-451 branch, under `manage.py runserver` on `127.0.0.1:8451`, against a scratch SQLite database filled by `seed_testing_data`, so no real user data;
    - the web build, `flutter build web --profile`, served on `127.0.0.1:8452`.

    Staging and production were **not** scanned. An active scan sends thousands of attack requests and could fill a shared database with junk a week before UAT, so I chose local only. The backend ran with `DEBUG=true`.

## Method

| Step | How |
|---|---|
| Headless ZAP | `zap-2.17.0.jar -daemon` with its own scratch profile, API on `127.0.0.1:8090` |
| Authenticated scanning | Signed in as the seeded demo Pengurus; a ZAP replacer rule added `Authorization: Bearer <token>` to every backend request, so the scan reached the authenticated endpoints, not just the public ones |
| Attack surface | Imported the backend's OpenAPI schema (`/api/schema/`), so every documented endpoint was scanned, not only the ones a crawler finds; then spidered the API and the web build |
| Scans | The passive scan, then a full active scan of the API (the default policy, 4 threads per host, at most 60 min; it finished in about 20) |
| Verification | Every Medium, and the Low that hinted at a crash, re-checked by hand with `curl` and against the deployed configuration |

The reports: [HTML](evidence/zap-report-2026-10-26.html), [JSON](evidence/zap-report-2026-10-26.json). They contain no token: I checked both for bearer tokens and JWTs before publishing.

## Findings

| # | Finding | OWASP (2021) | Severity | Whose code |
|---|---|---|---|---|
| 1 | Two announcement actions crash (500) on a missing or malformed id instead of answering 404 | A04 | Low–Medium | `apps/announcement` (PIL-243) |
| 2 | The backend CSP allows any HTTPS origin for scripts, styles, connections and frames | A05 | Medium | The CSP from pilah-be #129 |
| 3 | Swagger UI loads an unpinned `@latest` script and stylesheet from a CDN with no SRI | A08 | Low (debug-only page) | `config/urls.py` docs view |

### 1. A 500 instead of a 404 on `tarik` and `terbitkan`

ZAP sent the literal `id` where the OpenAPI schema has a UUID, and got a 500. Checked by hand as the demo Pengurus:

```console
$ curl -X POST .../api/v1/pengumuman/id/tarik -H "Authorization: Bearer …"
500  ValueError                     # malformed id
$ curl -X POST .../api/v1/pengumuman/00000000-0000-0000-0000-000000000000/tarik …
500  DoesNotExist                   # well-formed id that doesn't exist
$ curl -X POST .../api/v1/pengumuman/00000000-0000-0000-0000-000000000000/terbitkan …
500                                 # same for terbitkan, which ZAP missed (it needs a valid body)
$ curl .../api/v1/pengumuman/00000000-0000-0000-0000-000000000000
404                                 # the standard detail route is fine
```

**Cause.** Both custom actions skip the viewset's `get_object()`: they call `UUID(self.kwargs["pk"])` and then `Pengumuman.objects.select_for_update().get(...)` without handling `DoesNotExist`.

**Not an access-control hole.** The bank scoping is in the same `.get()`, so another bank's announcement fails the same way as a missing one, and the error reveals nothing about which ids exist. With `DEBUG=false` the body is a generic 500. The fault is error handling (CWE-755), which OWASP 2021 places under A04 Insecure Design and the 2025 list names A10, Mishandling of Exceptional Conditions.

### 2. `https:` in the backend CSP

```text
script-src 'self' https:; style-src 'self' https:; connect-src 'self' https:; frame-src https:
```

A scheme source matches every HTTPS origin, so an injected `<script src="https://attacker.example/x.js">` is allowed. That mostly undoes the CSP. API responses are JSON, which a browser never runs, so they need only `default-src 'none'; frame-ancestors 'none'`. The few HTML pages, the API docs and the OAuth popup, should list their exact origins.

### 3. Unpinned Swagger UI from a CDN

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/swagger-ui-dist@latest/swagger-ui.css">
```

`@latest` with no `integrity` hash runs whatever jsDelivr serves that day, on a page that holds the API's schema. The page only exists with `DEBUG=true`, which keeps the severity low.

### 4. No `script-src` on the web app

Production nginx sends `Content-Security-Policy: frame-ancestors 'none'` and nothing else. Since then, Pascal's [pilah-mobile #178](https://github.com/bank-sampah-PILAH/pilah-mobile/pull/178) adds a full policy. My [review of it](https://github.com/bank-sampah-PILAH/pilah-mobile/pull/178#pullrequestreview-5700286157) found it clean on every page but one, the draft PDF preview.

## Patch plan

Each fix is a test-first change, with the OWASP category named in its commit, as the earlier scan's plan was.

| # | Fix | Test first | OWASP | Status (29 Oct) |
|---|---|---|---|---|
| 1 | `tarik` and `terbitkan` load the announcement through the bank-scoped `get_object()`, which answers 404 for a missing or malformed id | For both actions: a missing UUID, a malformed id and another bank's id each get 404, never 500 | A04 | Planned. It's Aldo's code, so it needs a Linear issue and his agreement |
| 2 | JSON responses get `default-src 'none'; frame-ancestors 'none'`; the docs page and the OAuth popup list their exact origins | No `https:` or `*` in any directive; the OAuth popup and docs still load | A05 | Planned. Offered to Gabriel first, since #129 is his |
| 3 | Pin `swagger-ui-dist` to an exact version with SRI hashes, or serve it locally with `drf-spectacular-sidecar` | The docs page HTML has no `@latest` and an `integrity` attribute on each external asset | A08 | Planned |
| 4 | A full CSP for the web image | Pascal's header tests, plus a browser check of the PDF preview | A05 | **In progress** as Pascal's #178. My review asks for the preview to be fixed or sequenced first |

## How this compares with the 14 Oct scan

The [Metasploit scan](index.md) listed "no Content-Security-Policy" (its finding 4). A CSP has since been added, and ZAP now shows it's too broad. That's finding 2 here: the header exists, and its directives now need tightening. Metasploit, built for known exploits in known software, had little to say about a bespoke API. ZAP's application-level checks, run signed in and driven by the schema, are what turned up findings 1 and 3.
