## Method

Each scan is one command: [`tools/zap_scan.py`](https://github.com/mvfi0/pilah-docs/blob/main/tools/zap_scan.py), with a small per-feature **drive module** ([`pil428.py`](https://github.com/mvfi0/pilah-docs/blob/main/tools/zap_drives/pil428.py), [`pil435.py`](https://github.com/mvfi0/pilah-docs/blob/main/tools/zap_drives/pil435.py)).

| Step | How |
|---|---|
| Headless ZAP | `zap-2.17.0.jar -daemon` with a scratch profile, API on `127.0.0.1:8090` |
| Signed in | As the seeded demo Pengurus; a replacer rule adds the bearer token to every backend request ZAP sends |
| Attack surface | The OpenAPI schema imported, then the drive module's real requests sent **through ZAP's proxy**. For PIL-428: record two setoran, void one, void it again (409), void with an empty alasan (422), edit the voided one (409), read the list and riwayat. For PIL-435: the riwayat list for each `tipe`, with search, a custom period and the XLSX export. So the active scan attacks real ids and bodies, not schema placeholders |
| Scans | Spider of the API and web build, the passive scan, then the **active scan limited to the feature**: a ZAP context with `/api/v1/transaksi` (recursive: ids, `/batalkan`, PATCH) and `/api/v1/aktivitas` for PIL-428, and `/api/v1/aktivitas` and `/api/v1/transaksi/export` for PIL-435. Each recorded query-string variant was scanned on its own |
| Verification | Every 5xx in ZAP's history read from its response, not only ZAP's alerts; each real one reproduced with `curl`; the void's `alasan` tested by hand with attack payloads |

Reports: PIL-428 [HTML](evidence/zap-pil-428-2026-11-02.html) and [JSON](evidence/zap-pil-428-2026-11-02.json); PIL-435 [HTML](evidence/zap-pil-435-2026-11-02.html) and [JSON](evidence/zap-pil-435-2026-11-02.json). The script refuses to finish if a report holds a bearer token or a JWT, and I grepped all four as well.

### 1. NUL byte in `search`: a 500 on six endpoints

Reproduced by hand on the PIL-428 backend, as the demo Pengurus, with plain JSON requests:

```console
$ curl -H "Authorization: Bearer …" -H "Accept: application/json" ".../api/v1/aktivitas?search=ab%00c"
500
$ # the same for /transaksi, /transaksi/export, /pencairan, /nasabah and /jenis-sampah
$ curl ... ".../api/v1/aktivitas?search=abc"
200
```

**Cause.** Each list view reads `search` straight from the query string (`request.GET.get("search", "")`) and passes it to an `icontains` filter. PostgreSQL refuses text containing `\0`, and the `DataError` escapes as a 500.

Request **bodies** don't have this problem, because they go through DRF fields. The void's `alasan` with a NUL byte gets `422 "Karakter null tidak diizinkan."`, from `CharField`'s built-in `ProhibitNullCharactersValidator`.

**Impact.** No data is exposed: with `DEBUG=false` the body is a generic 500. But it's an unhandled exception any signed-in user can trigger at will, and each one logs an error. Rifqi's open [#144](https://github.com/bank-sampah-PILAH/pilah-be/pull/144) already validates the nasabah list's `search` with a `CharField`, which would turn that one endpoint into a 422 once merged. The other five remain.

### 2 and 3. Browsable-API crashes, debug-only

`config/settings.py` adds `BrowsableAPIRenderer` only when `DEBUG` is on, so these can't happen in production. Locally, anyone opening the API in a browser hits a 500:

- `ActivityHistoryView` is a `GenericAPIView` without a `queryset`;
- the setoran detail renders its PATCH form from `TransactionEditSerializer`, whose `alasan` is write-only input, not a model attribute.

Both also fail on unmodified `staging` (checked against `ee82c69`).

## What held up

- **The void's state machine:** every attack POST on `/batalkan` got 409 (already void) or 422 (bad alasan). The database afterwards held exactly the voids the drive made, one per run, with its own alasan, so no payload voided a setoran or changed a saldo. The roughly 610 `PATCH` attacks on the voided setoran got 409 or 422.
- **The alasan as data, checked by hand on fresh setoran:**

    | Input | Result |
    |---|---|
    | `<script>alert(1)</script>`, `' OR 1=1; DROP TABLE transaksi;--`, `=HYPERLINK("http://x","y")` | 200, stored and returned verbatim as JSON text: the ORM parameterises it, and Flutter renders it as plain text |
    | A NUL byte | 422 |
    | 256 characters | 422 (255 is accepted) |
    | Only whitespace | 422 "Alasan pembatalan wajib diisi" |
    | An unknown or malformed id | 404 |

    A voided setoran never appears in the XLSX or the statement PDF, so a formula in the alasan can't reach a spreadsheet. The exporter also guards user text against formulas.
- **Bank scoping:** another bank's setoran is 404, covered by the tests in [`f67aa72`](https://github.com/bank-sampah-PILAH/pilah-be/commit/f67aa72). ZAP signs in as one user, so it doesn't test this itself.

## How the method improved on 26 Oct

The 26 Oct scan imported the schema, so ZAP attacked paths like `/transaksi/id/batalkan`, which can only ever 404. This time:

- **Real requests:** the drive module sent the feature's real requests through ZAP's proxy, so the scan attacked a real setoran's void and edit.
- **History, not only alerts:** reading every response in ZAP's history found the NUL-byte crash, which ZAP doesn't report as an alert.

Three mistakes on the way, corrected before trusting the results:

- Git Bash rewrote `--scope /api/...` into a Windows path, so the first runs had nothing in scope.
- ZAP's active-scan API can't find id paths by URL, so the script now scans each prefix recursively.
- Its report API needs `|` between sites, not `;`, so the first reports came out empty.

The script now refuses a non-API scope and fails on an empty report.
