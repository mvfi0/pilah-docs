PIL-230: Edit Pencairan (correct a record, keep its history) Backend [#52](https://github.com/bank-sampah-PILAH/pilah-be/pull/52), mobile [#33](https://github.com/bank-sampah-PILAH/pilah-mobile/pull/33). **What it does:** a pengurus fixes a pencairan that was recorded wrong (nominal, tanggal, metode, keterangan). The old version is never lost. **In the app:** Riwayat → tap a row → "Edit Pencairan": - The form starts from the recorded values. - **Alasan perubahan** is required; Simpan stays disabled until you fill it. - Under the date picker: "Tanggal hanya bisa dimundurkan sampai …". The picker can't go earlier than that date or later than today. - The confirmation dialog warns that the saldo and later pencairan will be recalculated. - After saving, the riwayat reloads. The row shows *Diperbarui*, and its detail sheet gets a "Riwayat Perubahan" button listing each old version with its values, reason, who changed it and when. **Rules:** - A reason is always required. - An edit that changes nothing is rejected ("Tidak ada data yang diubah"). - **Tanggal:** can't be in the future, and can move back at most **7 days from the tanggal it was first recorded with**. Repeated edits can't push it further back. - **Saldo:** an edit is rejected if the saldo wouldn't cover this pencairan **or any later one**. Example: today's saldo might cover +Rp 20.000, but a pencairan made in between would then be short, so the edit is refused. - **Who can do what:** only pengurus of the same bank can edit or see the change history. A nasabah only ever sees the latest data (and the *diperbarui* flag in the API). **How it works:** 1. It locks the rows, validates, then saves the current version as a new `PencairanRevisi` row with the reason, editor and time. Revisions are never changed or deleted. 2. If the nominal or tanggal changed, it replays the nasabah's ledger from the earliest affected moment. The replay starts from a stored snapshot, because older opening balances have no transaksi behind them. It rewrites `saldo_sebelum`/`saldo_sesudah` for this pencairan and every later one, and moves `Saldo` by the difference. 3. All of it happens in one transaction: either the whole edit applies or nothing does. Later pencairan whose receipts were recalculated are **not** marked *Diperbarui*; only the edited one is. The 7-day limit is a single backend constant, and the app reads the resulting date from the API, so changing it needs no app release. **How the three fit together:** record (176) → list (222) → correct (230).
